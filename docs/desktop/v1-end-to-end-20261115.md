# Future-attempt-only v1: real transport to headless view — 2026-11-15

The owner selected future-attempt-only v1 for the initial implementation.
Bounded-prefix/seamless mid-attempt recovery is deferred. Production streaming
remains disabled pending exact-head independent review, protocol/compatibility
and acceptance gates. No preference, CLI or environment switch enables it.

The view now keeps a persistent readable policy notice while a future-attempt
client is attached: attaching or reconnecting mid-answer shows persisted history
until the answer completes or the next eligible attempt. The notice explicitly
states that older daemons use persisted history. Unlike transient status text,
action notices and fresh status reads cannot remove it. Future-mode connection
and accepted-baseline status also use consistent wording; installing a live
baseline no longer labels that accepted view “live token streaming unavailable”.
Canonical-only older-peer fallback keeps its canonical status.

## Actual path validation

The new feature-gated test attaches a real Client to a private real Daemon and
loopback fake Anthropic SSE provider, then drains its updates through the actual
Shell view in GPUI TestPlatform. It does not inject transcript events or snapshots
at the view seam. Three controlled Runs establish these boundaries:

1. Start a Run before attachment. After the UI selects its Session, only the
   persisted user message is shown. Releasing completion displays the complete
   persisted assistant answer once.
2. Start a future eligible Run. Its partial answer becomes a real provisional
   view row. Reconnect through the real Client command; its physical connection
   changes, the old prefix is retired, and the accepted baseline contains only
   persisted history. Release another chunk from the still-active producer;
   the view remains canonical-only until completion. Completion installs the
   full persisted answer, including its formerly unseen prefix, exactly once.
3. Start the next eligible Run after reconnect. Its prefix streams again, then
   reconciles to its exact persisted answer.

The same composer entity and exact unsent Thai/emoji draft survive all phases.
There are exactly three fake provider requests and six persisted messages at
completion. Runs are started explicitly by the private fixture; this case tests
the provider-to-view streaming path, not native Send/consent interaction.
Existing Client/forecast tests cover those separate mutation boundaries.

A second actual-IPC-to-view fixture advertises no future capability and fails
if it receives an unsupported or mutating request. It verifies canonical-only
subscription, persisted output, no live owner and canonical unavailable status.
It uses a controlled old peer, not an actual historical daemon binary.

A third TestPlatform case verifies the persistent notice remains readable and
the composer reachable at 200% in the minimum 480 × 360 reflowed window. Synthetic
font metrics and input do not prove human/native scaling or accessibility.

The real connection/reconnect validation entry points require both `test-support`
and `daemon-tests`; neither is wired into the normal app. Production
`Client::start` still uses canonical-only policy. The wire protocol, producer,
lockfiles, manifests and dependencies are unchanged. A later bounded-prefix
protocol can negotiate a separate version without weakening v1 or legacy fallback.

## Limits and next gates

The post-reconnect negative visibility check is a bounded observation after the
real producer clock advances, not a proof over every scheduling delay. The
separate deterministic cutoff/canonical/ownership schedules and private IPC
adversarial cases supply the ordering checks. The initial fake-provider request
is held before attachment; no existing prefix is synthesized or replayed.

These cases execute a synthetic headless view with real private transport and
persistence. No native renderer, foreground window, real Profile, Tool, paid API,
OS keyboard/IME/clipboard or screen reader executes. The existing foreground
approval `proud-river-57508678` and uncertain launch/control remain unresolved and
untouched. The original conflicting checkout and all other writers are preserved.

Exact-head combined review, supported-host protocol/compatibility execution,
native input/accessibility/scaling/filesystem, required parity, accepted native
performance budgets and licensing/distribution gates still apply. There is no
new current-head package, signing/install/launch acceptance, remote publication
or merge. See the [production plan](production-streaming-plan-20261115.md) for the
ordered enablement steps. V1 scope selection does not clear these later gates.
