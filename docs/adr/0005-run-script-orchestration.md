# The agent may run ad-hoc orchestration scripts that call Tools but hold no Capabilities

A built-in, `run_script`, lets the agent submit one QuickJS script per step that calls registry Tools as async functions, so loops, filters, branches and parallel fan-out run in the sandbox instead of costing one model round trip each, and intermediate results never enter model context. The script holds **no Capabilities of its own**: it gets no `fetch`, `fs`, `process`, `env`, `clipboard`, `notify`, `llm`, `agents`, `store` or `emit`, only the Tools named in its `uses` list plus `console`, `JSON`, timers and `requireModule`. Every effect still happens inside a persisted, versioned, approved and measured Tool, so ADR 0002's premise holds: capability grows only in the registry. A script that proves useful is promoted into a real Tool through the normal `create_tool` gate (`save_as`), and scripts that recur across Sessions are flagged to the agent and the prompt-proposal generator. To make fan-out real, `tools.call` returns a Promise, and each nested Invocation runs on its own thread, bounded by `scripts.max_parallel`. We rejected a general code sandbox with Capabilities, which would recreate the starter shell ADR 0002 rejected and let scripts replace Tools. We also rejected exposing Tools only as a code API with no direct function calls, as Cloudflare Code Mode does: `find_tools` declaring real functions keeps the cached prompt prefix stable and shows the provider exact schemas.

**Status:** accepted

**Considered Options:** no code mode (status quo; parallelism only through provider-emitted parallel tool calls); a script sandbox with its own declared Capabilities; code-API-only Tool exposure (Codex / Cloudflare Code Mode); a script built-in with no Capabilities (chosen).

**Consequences:**

- **Composition API.** `tools.call` becomes asynchronous everywhere, so scripts, saved scripts and hand-written Tools share one API and composed Tools fan out in parallel by default. This was possible because no release had shipped Tools that used its old synchronous return value. A forgotten `await` would otherwise pass a Promise off as data, so a Tool or script that finishes with a call still pending fails instead of succeeding.
- **Approval.** It moves from per tool call to the declared `uses` set, checked before the script runs. A call outside that set is refused by the daemon, not just by the script's wrapper. A Tool with input-bound scopes is still approved per call for what it binds.
- **Recording.** Scripts are recorded in their own `scripts` table, not as Invocations, because Invocations belong to registry Tools. Nested Invocations point to their script through `parent_id`, and token attribution splits the script's share over them. Scripts are never optimised or replayed, so the bootstrap prompt steers the agent toward saving any script it would run twice.
